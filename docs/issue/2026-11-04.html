Claude 推出 Message Threads（公開 beta）：長對話只送新訊息，首字延遲中位數約降 35%

Claude 官方文件、TLDR AI・11/3

我讀了官方文件頁面，並參考 TLDR 的摘要。官方文件說：以前每一輪都要把整段對話重新上傳，API 也要重新驗證與 token 化；現在可在 Messages API 加一個 `thread` 參數。第一次請求照舊送完整對話並加 `"thread": {"type": "create"}`，之後每輪只送新訊息，加 `"thread": {"type": "continue", "previous_message_id": "<上一個回應 id>"}`。需要 beta header `message-threads-2026-08-12`。TLDR 轉述的數字（官方說法，我沒看到原始量測方法）：輸入 500K 到 1M token 的請求，首字時間（TTFT）中位數降約 35%，token 用量不變。

白話：白話：跟 AI 聊很久的時候，原本每說一句，都得把前面全部內容重新寄一遍。現在伺服器暫時幫你記著，你只寄新的那一句，所以起跑更快、送的資料更少。
💡 為什麼重要你日常用 Claude Code 與自己做的 agent，長對話的等待時間與重送成本是真實痛點。這是 API 層的功能，要自己寫 agent 迴圈（例如個人 AI 助理）才直接用得到。
🎯 對你的影響　👀 值得追蹤
你的個人 AI 助理若自己管對話迴圈，且對話常長到數十萬 token，這功能可能降低等待時間（推測）；Tap Diary 與日報網站目前看不出用得到。
▶ 等你要優化個人助理時，先讀 docs.anthropic.com 的 Message threads 頁面，用 SDK 的 `client.beta.messages.thread(...)` 改寫一個最小對話迴圈，並自己保留完整對話以便 404 重建。
📖 展開完整解析（6 段）

怎麼用

三步：create（送完整對話、system、tools，伺服器以回應 id 存起來）→ continue（只送新訊息與上一個回應 id，system 與 tools 不可再送，連 null 也不行，否則 400）→ replay（若 thread 已失效，continue 會回 404，要用完整對話重新 create）。文件說 SDK 有 thread helper 會自動處理 replay，並替你加 beta header；helper 只把對話放在記憶體。

有效期限與限制

文件寫明：thread 是盡力而為（best-effort），最後一次請求後 5 分鐘過期，最晚在最後使用後 1 小時內刪除；每個被儲存的回應會重新計 5 分鐘。所以你的應用程式必須自己保留完整對話，才能在 404 時重建。回應本身不會告訴你這一輪有沒有被存下來，要到下一次 continue 才知道。

哪些欄位要一致

model、tool_choice、thinking、mcp_servers（授權 token 除外）、context_management、output_config、top-level cache_control 與 beta 值，每次都要與 create 時相同，否則回 400 並帶 `thread_fingerprint_mismatch`。max_tokens、stop_sequences、stream 等可每輪變。MCP 伺服器網址與授權 token、container id 不會被儲存，要每次送。

與提示快取的關係

文件的範例在頂層加 `cache_control: ephemeral`，讓每輪都用提示快取；沒加的話，後續輪次仍只送新訊息，但不會有快取，除非你自己加快取斷點。這與第 1 週學的 KV cache／提示快取是互補：thread 省的是『上傳與重新驗證』，快取省的是『模型重算前綴』。

資料處理

文件標示不符合 ZDR（零資料保留）與 HIPAA。若你的資料有這類要求，這是需要先確認的限制。

35% 的數字只來自 TLDR 轉述，我沒有找到原始量測；範例與欄位以文件為準，我沒有實際呼叫 API 驗證。

CWE-bench v2 公開 100 題資安修補任務：領先模型 pass@1 約 67.8%，仍有 19% 題目每次都失敗

Hugging Face 部落格（Collinear AI）・11/3

我讀了原文。CWE-bench v2 給 agent 一個真實開源專案的程式碼與簡短指令，目標是找到並修掉安全弱點，同時不破壞原有功能；評分全程式化、可重現。公開集有 100 題、涵蓋 91 種 CWE，另有不公開的保留集。作者（出題團隊自己）公布 11 個模型的結果：Gemini 4 Argon 領先，pass@1 67.8%、pass@4 81.0%；Claude Opus 5.5 為 67.3% 與 78.0%。95 題至少有一個模型解出，但領先者仍有 19% 的題目四次都失敗。成本方面：DeepSeek V4.1 Flash 每次約 $0.04、pass@1 57.0%，Opus 約 $1.83，Gemini 約 $3.92。

怎麼出題與驗證

每題是一個 Harbor 任務（Docker 環境＋指令＋確定性驗證器）。作者說每題檢查：指令像真實需求、每個被評分的行為都能從指令推得、驗證器檢查行為而非特定修法、起始碼失敗而參考修補通過、原功能仍正常、驗證器能擋住照抄上游已知 patch 的記憶解法；並說每題都人工審過，且用 LLM 評審團調整難度與公平性。

📘 今日一課 · 12 分鐘

pass@k 是什麼？怎麼讀 benchmark 的分數

為什麼今天學這個

今天的 CWE-bench v2 同時報告 pass@1、pass@4 與每次成本。這剛好銜接下週第 3 週「評測與選型」的第一個主題（benchmark 怎麼看）；第 2 週已全部上完，所以提前預習。以下為一般原理，除了引用今天文章的數字，非來自該文；公式小程式我有實際執行。

是什麼

pass@k 的意思是：讓模型對同一題試 k 次，只要其中至少一次通過驗證，就算這題過關；全部題目的過關比例就是 pass@k。pass@1 是『一次就對』的比例，最貼近你平常用 AI 的體驗。

為什麼要看

模型輸出有隨機性，同一題多試幾次結果會不同。今天文章中領先模型 pass@1 為 67.8%、pass@4 為 81.0%：代表它『一次通過』約 2/3，但給 4 次機會就多拿了約 13 個百分點。兩個數字回答不同問題：pass@1 是日常可靠度，pass@4 是『若有自動驗證器、可重試』時的上限。

怎麼算

常見做法是每題跑 n 次、其中 c 次通過，再用公式估計：pass@k = 1 − C(n−c, k) / C(n, k)（若 n−c < k 則為 1）。例：n=4、c=2、k=1 得 0.5；k=4 得 1.0。這是從 Codex 論文以來常用的無偏估計；今天文章是 4 次平均，我沒看到它的具體算法。

怎麼讀才不被騙

1) 看 k 與題數：100 題的小資料集，1 個百分點只是一題的差距，噪音很大。2) 問有沒有驗證器：pass@k 的重試只有在能自動判對錯時才實用，否則你得自己檢查。3) 一起看成本：今天文章中約 $0.04 對 $3.92 每次，表現差約 11 個百分點，要不要付差價取決於你的任務。4) 出題者通常也是維護排行榜的人，且資料集可能被模型見過，保留集比較可信。

和選型的關係

選模型前先定義自己的『一題』是什麼、能否自動驗證、可以重試幾次，再用對應的指標，而不是只看排行榜第一名。

（已實際執行）pk(4,2,1)=0.5、pk(4,2,4)=1.0、pk(4,1,2)=0.5、pk(4,0,4)=0.0。
