PHP2Shell：一個 2024 年就被回報的記憶體錯誤，在 AI 協助下兩週內被串成可執行任意程式碼的漏洞

IEEE Spectrum・11/4（HN 994 分、603 則留言）

我讀了 IEEE Spectrum 的報導（未讀 HN 留言）。報導說 PHP2Shell 是 PHP 的漏洞，可能讓攻擊者讀取敏感資料並在主機上執行惡意程式碼。根源是一個 out-of-memory（配置記憶體過小）錯誤，2024 年就回報給 PHP Foundation，但因為通常只會讓程式當機而被擱置。資安公司 Calif 受 OpenAI 贊助獨立稽核 PHP，稽核開始後兩週內，研究員借助 AI 工具把這個錯誤變成任意程式碼執行；Wiz 確認並擴大了漏洞範圍。PHP Foundation 在惡意利用前發布修補，據報導四位工程師花兩個月完成修補，10 月底揭露。

白話：白話：有個老 bug 一直被當成『只會閃退』的小問題沒人修；這次有人用 AI 幫忙，很快找到把它變成『能遠端操控伺服器』的方法。
💡 為什麼重要網路上大量舊網站仍跑 PHP（WordPress、Drupal 等）。更廣的意思是：AI 降低了『把低風險 bug 升級成高風險』的成本，過去沒人修的 crash 報告價值要重估。
🎯 對你的影響　🔧 可立即用
如果你架過或維護任何 PHP 站台（含 WordPress，推測你或身邊專案可能有），這是需要更新的警訊；Tap Diary（Flutter）與日報網站（靜態頁）本身不受影響。
▶ 今天檢查是否有跑 PHP 的主機：執行 `php -v` 看版本，到 PHP 官方安全公告頁確認該版本是否已有 PHP2Shell 對應修補，有就立刻升級。

漏洞怎麼來的

報導描述：out-of-memory 類錯誤通常只導致崩潰，所以長期被忽視。Columbia 大學的 Suman Jana 在文中說，很多當機回報沒人處理，因為大家不當真。

AI 扮演什麼角色

報導說，利用過程需要精準的記憶體定位與覆寫順序，這類很具體的推理 AI 做得『很好』；但文章也強調仍需要深厚的資安與 PHP 專業，AI 無法獨自完成，它的作用是讓頂尖專家能做更多事。Jana 估計約前 0.1% 的專家受益最大。

攻防不對稱

Jana 指出找洞與補洞不對稱：修補必須封住所有攻擊路徑又不能破壞既有功能。本案修補據報導耗時兩個月、四位工程師，而利用只花兩週。

修補的方向

報導提到自動修補加形式化驗證：AI 產生修補與證明，再由非 LLM 的證明檢查器驗證，因為 LLM 會幻覺。並提到 Anthropic 10 月 22 日的形式化驗證發布作為例子（我沒讀該發布）。

各方觀點

Tolmo 的 Matt Suiche 說，人類 40 年來寫的舊軟體正被暴露；Johns Hopkins 的 Matthew Green 較悲觀，認為要等更糟的事件（他猜可能 2027 初）才會改變。建議包括：讓防守方取得前沿模型與 token 額度，以及『更新就對了』。

Realtime-Bench：50 個即時互動任務，最強模型在真實時鐘下只有 36%，暫停時鐘則約 70–80%

Import AI 479・11/2

我讀了 Import AI 的摘要，沒有讀原論文。該基準有 50 個互動任務（30 個網頁、20 個遊戲），測三種能力：追蹤隨時間變化（RT-Perceive）、依可用時間調整思考量（RT-Deliberate）、掌握動作時機（RT-Act）。有三種時鐘：真實時鐘（含實際延遲）、暫停時鐘（模型思考時世界不動）、token 時鐘（每生成一個 token 時間前進）。摘要說，真實時鐘最高分是 GPT-6 Astra（high）的 36%；暫停時鐘下高推理模型約 70–80%，代表差距主要來自時間壓力。

白話：白話：現實世界不會等 AI 想完才動。同一個模型『允許無限思考』時能做對七八成，但世界照常運轉時只剩三分之一。
💡 為什麼重要做機器人、即時感知或遊戲／UI 代理人，延遲與思考預算是核心設計條件，不只是模型準不準。
🎯 對你的影響　👀 值得追蹤
若你做感知＋LLM 的機器人或即時助理，這是選型時要考慮延遲的依據（推測）；日報與 Tap Diary 無關。
▶ 之後設計即時代理人時，先量『首字延遲＋總延遲』，並設定一個思考時間上限；今天的一課有簡單量測方法。
📖 展開完整解析（4 段）

三種時鐘的意義

暫停時鐘量的是『能力上限』；真實時鐘加入推理延遲；token 時鐘是模擬方式，讓結果不受機器速度影響（這是我對摘要的理解，原文細節沒讀）。

差距的來源

摘要說差距主要是時間壓力，不是不會做。這與『多想會更準，但來不及』的取捨一致。

與你的背景相關

機器人控制迴圈常是毫秒級；LLM 多為秒級。這類基準量化了落差，也暗示需要快慢分層（小模型快速反應、大模型慢速規劃）——這是推測，不是摘要的結論。

限制

只有 50 題，分數噪音大；官方（作者）說法，我沒看到第三方重現。

DreamX：把影片擴散模型當成通用「潛在動作」學習器，每幀壓縮 300 倍

arXiv cs.RO／cs.CV・11/3（僅讀摘要）

我只讀了 arXiv 摘要，沒讀全文。DreamX 用預訓練的影片擴散模型，從其時空特徵取出緊湊的潛在動作；每個潛在影片幀從 1,200 個 token 壓到 4 個（300 倍）。目標是讓動作表示能跨人類與機器人、跨環境與動作參數化共用。摘要聲稱在 LARY-Bench 上於潛在動作模型中達到最佳，但沒給具體分數；並稱能做任意到任意的影片轉移與零樣本動作轉移，且在潛在動作空間訓練策略能降低基於影片擴散的策略之運算成本。

白話：白話：不靠人手標註『這段影片裡做了什麼動作』，而是讓影片生成模型自己學出一種通用的動作編碼，人的影片和機器人的影片可以共用。
💡 為什麼重要這與你的 CV／機器人背景最貼近：用大量人類影片教機器人，是降低遙操作資料成本的熱門方向。

核心想法

影片生成模型已學過物體如何隨動作變化；把這份先驗拿來分離『動作』與『外觀』。

壓縮

每幀 1,200→4 個 token 是摘要唯一的具體數字，代表動作被表示得非常精簡。

聲稱與缺口

最佳成績沒有數字，零樣本轉移的難度與任務設定要看全文；摘要是作者自述，未見第三方驗證。

延遲怎麼量：首字延遲、總延遲與思考預算

為什麼今天學這個

今天 Realtime-Bench 顯示同一批模型在真實時鐘下表現大跌，這正好銜接第 3 週「評測與選型」的「成本與延遲」。以下為一般概念；除引用今天文章數字外，非來自該文；量測小程式我沒有實際執行。

是什麼

延遲有兩個常用數字：首字延遲（TTFT，送出請求到第一個 token 回來）與總延遲（整段回答完成）。串流輸出時使用者感受主要看 TTFT；要把結果交給程式或控制迴圈時，看總延遲。

為什麼重要

今天的基準把時間壓力拉進評分：模型在暫停時鐘約 70–80%、真實時鐘最高 36%（作者摘要說法）。這說明『準確率』與『在時限內的準確率』是兩個指標。

怎麼運作

總延遲大致等於：排隊與網路 + 讀取輸入（輸入越長越久）+ 逐 token 生成（輸出越長越久）。推理型模型會先產生很多『思考 token』，所以同一題可能慢數倍。這是一般概念，各供應商實作不同。

怎麼選

先決定你的時限：聊天可容忍數秒；機器人控制迴圈常要毫秒級，LLM 通常只適合放在慢速規劃層，快速反應交給小模型或傳統控制（推測性建議）。再在該時限下比較準確率與成本，而不是只看排行榜。

10 分鐘小實作

用你常用的 API 或本地模型，對同一個提示各跑 5 次，記錄 TTFT 與總時間，再各換『低／高思考預算』比較。

動手做（勾選記錄進度）
