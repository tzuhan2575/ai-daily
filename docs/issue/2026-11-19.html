Google 發布 Gemini 4 Neon：每百萬 token 輸入 3、輸出 15 美元，官方稱 Artificial Analysis 智力指數第 3、程式代理指數第 1

Google 官方部落格（已讀全文文字，示範影片與圖表沒看）＋HN 討論（293 分、277 則留言，讀了前 12 則頂層留言）・11/18

Google DeepMind 推出 Gemini 4 Neon，定位在 Carbon（最難、最長的任務）和 Hydrogen（快速日常）之間。價格是每百萬 token 輸入 3 美元、快取輸入 0.15 美元（比一般輸入便宜 95%）、輸出 15 美元，上下文 100 萬 token，當天就上 Gemini API（AI Studio）、Gemini for business、Antigravity 與 Gemini App。官方引用的第三方成績：Artificial Analysis 智力指數 61 分（xhigh 思考等級，總排第 3）、Coding Agent Index 58.6 分（第 1）、Vals Index 70.9%（第 2）、Terminal-Bench 4.1 65.2%。官方說在預設 high 等級下，每個任務成本比 Carbon 低 32%，比其他前沿模型低約 50% 到 80%。資安版『Neon for cyber』只開放給 Fairwind 計畫的防守方。

白話：白話：Google 這個月又出一個新模型。它不是最大最強的那個，而是『夠聰明、又快又便宜』的中間款，主打跑長時間的寫程式 agent。價格大概是同級旗艦的一半上下。
💡 為什麼重要你日常用 Claude Code，這類『便宜一半、分數接近』的模型會直接影響你要不要在日報或個人助理的某些步驟換模型。不過分數幾乎都是 Google 自己挑的，社群對實際手感意見分歧，值得自己用小 eval 測。

定位：三兄弟各管一段

Google 現在把 Gemini 4 分成 Carbon（最難、最長的專案）、Neon（深度與效率平衡）、Hydrogen（快速日常執行）。Neon 可以單獨跑，也可以在 Antigravity 裡當『協調者』，指揮一群平行的 Hydrogen 子代理。官方說它會減少重複讀檔、工作時回報進度、長對話裡做上下文壓縮也比較穩。思考等級有四段，可依工作調整智力與 token 花費。

官方給的分數

除了上面提到的指數，Google 還列了：Legal Research Bench、Tax Agent Bench 第 1；Chartography（讀專業圖表）73.5%；Agents' Last Exam v1.1 75.8%；Zapier AutomationBench 56.3%（第 1）；Arena 新的 Agent Arena Index 1336 分（第 2，超過 4,200 次真實 agent 對話）；Terminal-Bench Science 70.5%。SWE-sweep 上，用 mini-SWE 框架是 12.8%，換成 Google 自家 Antigravity 框架變成 39.0%——同一個模型差三倍，再次說明『框架』本身影響很大。

安全與資安

官方說：Terminal-Bench 4.0 作弊率 0.0%、內部寫程式作弊評測抄捷徑 2.45%（Gemini 4 系列最低）、agent 安全套件誤動作率 0.09%；在 Gray Swan 的間接提示注入評測中，開最高思考等級加上即時防護時攻擊成功率 0%。資安方面，SEC-bench Pro 90.5%、CWE-bench v2 70.7%、WebExploitBench v1.2 51.26%。這些都是 Google 自己的說法，第三方複測我沒看到。

社群反應

HN 上：一位自稱在 Artificial Analysis 工作的留言者說，Neon 總分高於 Carbon，但在 CritPt 這類研究級推理評測上比較低，所以 Carbon 仍是『長程』模型，選模型只會越來越難；有人實測 OpenRouter 上 Neon 每秒約 127 token，Carbon 只有約 46；有人看 Vals 比較說它略低於 Fable、略高於 Opus 5.5；也有人說用起來還是覺得 Opus 5.5 比較像在跟同事講話。另一個熱門抱怨是模型名稱太多（Sol、Astra、Neon、Carbon、Fable……）根本對不起來。

觀察點

① 第三方（Artificial Analysis、Vals、LMArena）完整數據與實際每任務成本；② 在 Claude Code 以外的 agent 框架裡能否重現 Antigravity 的成績；③ Neon for cyber 的開放範圍。

The Washington Sun 報導（已讀全文，引述三位匿名消息人士）・11/17；HN 討論（95 分、56 則留言，讀了前 10 則）

根據 The Washington Sun 引述三位知情人士：華爾街高層與美國國家安全局（NSA）私下告訴國會議員，本週一連串大規模當機（全美航班停飛、銀行客戶無法登入、NSA 一個高度機密通訊網路中斷）不是網路攻擊，而是急著修補『AI 模型找到的漏洞』，一次推太多修補把系統壓垮。報導引述《華爾街日報》說，FAA 因全國停飛取消超過 2 萬個航班；微軟 Outlook 也大當機，微軟說是技術缺陷。JPMorgan 週一說是軟體 bug，NSA 週二說是『例行維護』。

白話：白話：AI 很會找系統的漏洞，大家怕壞人也用 AI 先找到，所以拼命趕著修。可是很多是老舊系統，修補一次推太多、測試不夠，結果自己把服務弄壞。注意：報導說的是『修 AI 找到的漏洞』出事，不是 AI 寫的修補出事。
💡 為什麼重要這是『AI 找漏洞的速度 > 人類安全上線修補的速度』第一次被說成大規模當機的原因。對你來說，重點是：即使是個人專案，AI 幫你找到問題後，也要有測試、分批上線、能快速回滾，不要一次全推。

我讀到什麼

讀了 The Washington Sun 報導全文。報導的核心來自匿名消息人士，各機構公開說法（JPMorgan 說軟體 bug、NSA 說例行維護、微軟說技術缺陷）與之不完全一致；FAA 停飛的原因報導本身也說『不清楚』。所以因果關係目前只是轉述，沒有官方確認。

報導中的說法

一位聽取簡報的國會官員說：『這些模型找到大量漏洞，讓大家更急著馬上修補……一次要推的修補比系統設計能承受的還多。』國土安全部長在 CNBC 說：『他們在很舊的電腦系統上推新科技，似乎把系統壓垮了，新科技推出時我們會看到更多這種事。』Encode 的 Nathan Calvin 說，這某種程度令人安心（不是攻擊），但顯示關鍵基礎設施建在有大漏洞的舊系統上，而且模型越強，會持續找到更多漏洞。

1800 億參數模型跑在 32 GB 的 Mac 上：Hugging Face 讓 Transformers 直接從 SSD 串流 MoE 專家，速度追到 Strata 的 94%

Hugging Face 官方部落格（作者 Tarek Ziadé，已讀全文文字，示意圖沒看、Space 與 PR 沒讀）・11/18

Hugging Face 工程師在 Transformers 加了實驗功能（PR #50717）：MoE 模型的『專家』權重留在 SSD，router 選到哪幾個專家才讀進一個固定大小的快取。以 Qwen3.8-Flash-Next（約 180B 參數，48 層、每層 512 個專家、每 token 啟用 10 個，FP8 專家共 121 GB）為例，把專家量化到 3 bit（磁碟 49 GB、裝置上快取 12 GiB），在 32 GB 記憶體的 MacBook M5 上跑到解碼每秒 13.9 token、4K 提示預填每秒 228 token；專用引擎 Strata 是 14.8 與 220。作者也在 24 GB 的 A10G 上比較 Qwen3.6-35B-A3B：Strata Q8 每秒 82–88、llama.cpp Q8 63–64、vLLM 最佳設定 20.1、Transformers 原本的 Accelerate 卸載只有 0.16。

白話：白話：MoE 模型很大，但每個字其實只用到一小部分『專家』。所以不必把整個模型塞進記憶體，只要把『現在要用的那幾個專家』從硬碟搬進來、常用的留著就好。這篇示範用這招讓筆電跑超大模型，雖然每秒 14 個字，對寫程式 agent 來說還是太慢。
💡 為什麼重要接續第 4 週『本地跑小模型』：這篇把『模型放不進記憶體時各家引擎怎麼辦』講得很清楚，也給了實測數字，是你之後評估在本機或自己 GPU 跑大模型時的好參考。
🎯 對你的影響　👀 值得追蹤
你若想在自己的機器上試超過記憶體的 MoE 模型，這篇的比較表能幫你選引擎：專家放得進 RAM 先用 llama.cpp，放不下才考慮串流（推測）。
▶ 下次本地跑 MoE 模型時，先算『專家總大小 vs 你的 RAM』，放得下就試 llama.cpp 的 --fit on；這個 Transformers PR 還沒合併，先不要用在正式工作。

我讀到什麼

讀了部落格全文文字；文中提到的 Transformers PR、Hugging Face Space 的完整基準與原始結果沒讀，一張單層運作示意圖沒看。所有速度數字都是作者自己測的，作者也說明 API 還在跟 Transformers 維護者討論，可能會改。

各引擎怎麼處理『放不下』

llama.cpp：用 mmap 載入 GGUF，可把專家留在 CPU 計算（--cpu-moe、--n-cpu-moe N、-ot "exps=CPU"，或 --fit on 自動決定），只有中間結果過 PCIe；專家放得進 RAM 時很難被打敗，放不下時 page cache 會一直換頁。vLLM：--cpu-offload-gb N 把權重放在 pinned RAM、每個 token 透過 PCIe 讀，沒有快取也沒有磁碟層；加 --cpu-offload-params experts 只卸載專家能快一倍。Transformers 原本透過 Accelerate 一次搬整個模組，MoE 層等於每個 token 搬全部專家，只為了用其中 8 到 10 個。

關鍵技巧：把快取變成『插槽池』

第一版用 Python 迴圈一次算一個專家，即使全在快取裡也只有每秒 10.1 token（原版約 32）。解法是預先配置一塊所有層共用的裝置記憶體當插槽池，再維護『專家編號 → 插槽』對照表；把 router 選出的編號換成插槽編號後，原本一次算完整層專家的 grouped_mm 核心就能直接用。之後再加上 8 條 I/O 執行緒讀取缺頁的專家、提前跑後兩層的 router 猜測要預取哪些專家。

從每秒 10 到 14 token 靠什麼

大部分時間其實不是花在專家：MPS 上 PyTorch 會累積小核心直到下次同步，強制提早提交多了 10%；為 Gated DeltaNet 等寫 Metal 核心；改用 Strata 的 GGUF 權重，讓每 token 的稠密權重流量從 5.4 GB 降到 3.9 GB；預填用更大的區塊並在計算當層時預讀下一層專家。剩下差距主要是每 token 約 10 毫秒的主機來回，作者說要 PyTorch 在 MPS 串流上提供原生同步操作才能解決。

作者自己的結論

每秒約 14 token 對他使用 coding agent 的方式還是太慢，真正的工作仍交給家裡兩張 RTX 4090 跑 Qwen3.8-27B。他說這次的程式碼（PR、模型專用套件、Metal 核心）都是 AI 寫的，他負責決定試什麼、看效能剖析、決定留什麼。

觀察點

① PR #50717 是否合併、API 定案成 device_map={"experts.*": "disk"} 的形式；② 3 bit 專家量化對品質的影響（文中只給了稠密層 8 bit 的困惑度 +0.2%，專家量化的品質數字沒給）。

權限與沙箱：讓 agent 跑的指令『只碰得到該碰的檔案』

為什麼今天學這個

本週是第 5 週「Agent 安全與權限」，前三天已經講了提示注入、確認閘門、網路與金鑰隔離，今天補上最後一塊『權限與沙箱』，把整週串起來。今天的新聞剛好呼應：OpenAI 發表《Inside the Codex sandbox》，說明 Codex 在 macOS、Linux、Windows 上怎麼對指令強制套用檔案與網路限制（原站擋爬蟲，我只讀到 RSS 摘要，細節沒讀）；Gemini 4 Neon 也強調『不越界』的安全評測。本課改用我讀過全文的 Claude Code 官方沙箱文件，因為那是你每天在用的工具。範例的設定檢查腳本我在本環境實際執行過；Claude Code 裡的 /sandbox 與 bubblewrap 沒有實際執行（本環境沒有安裝 bubblewrap）。

是什麼

『權限』決定 agent 的某個動作要不要執行（例如跳出確認視窗、或用 allow／deny 規則自動決定）；『沙箱』則是作業系統強制的圍牆，決定一個指令『執行之後』能碰到哪些檔案、能連到哪些網路。兩者是不同層：權限是門口的警衛，沙箱是房間的牆。警衛可能被說服放行（例如提示注入、或你按太快），牆不會。Claude Code 的 Bash 沙箱預設是關的，用 /sandbox 指令或在設定檔把 sandbox.enabled 設成 true 開啟。

為什麼需要

11/17 那課講的確認閘門有個問題：如果每個指令都問，你很快會習慣性按『是』。沙箱換個思路：把指令關在圍牆裡，牆內的事就讓它自動跑（Claude Code 稱為 auto-allow 模式），只有要出牆的才問你。這樣確認視窗變少，但每次跳出來都真的值得看。而且像 11/18 的 PyPI 竊密事件，惡意程式是在你跑 pytest 時偷偷執行，根本不會經過確認視窗；只有沙箱這道牆能限制它寫哪裡、連去哪。

怎麼運作：預設擋了什麼、沒擋什麼

依官方文件，開啟後的預設是：寫入只限工作目錄、每位使用者的暫存目錄、以及你用 --add-dir 加入的目錄；讀取則是『機器上大部分都讀得到』，包括 ~/.ssh 與 ~/.aws/credentials；網路沒有直接出口，所有連線都經過本機代理，依 allowedDomains 白名單檢查，名單一開始是空的；環境變數則照樣繼承，包含裡面的秘密。換句話說：預設主要擋『寫』和『連網』，『讀秘密』要你自己用 filesystem.denyRead 補上。macOS 用內建的 Seatbelt，Linux 與 WSL2 用 bubblewrap 加 socat；原生 Windows 不支援，要在 WSL2 裡跑。

三個容易忽略的漏洞

① 沙箱只包 shell 指令：Read、Edit、WebFetch 這些內建工具、hooks、本機 MCP 伺服器都在沙箱外，要靠權限規則管（denyRead 擋不了 Read 工具）。② 逃生口：指令在沙箱裡失敗時，Claude 可以用 dangerouslyDisableSandbox 要求在沙箱外重跑；把 allowUnsandboxedCommands 設成 false（/sandbox 的 Overrides 分頁叫『Strict sandbox mode』）就會關掉。③ 起不來就裸跑：平台不支援或相依套件檢查失敗時，預設會『不用沙箱』繼續跑，要設 failIfUnavailable 為 true 才會直接結束。另外 excludedCommands 裡列的指令（例如 docker）也是沙箱外執行。

和本週其他三課怎麼拼起來

一個比較完整的組合：沙箱（牆）限制寫入與連網 → denyRead 與憑證遮蔽讓牆內讀不到真金鑰（11/18 課）→ 對 git push、刪除等不可逆動作保留 ask 規則，在 auto-allow 模式下依然會跳確認（11/17 課；官方文件明確說內容型 ask 規則如 Bash(git push *) 仍會強制詢問）→ 外部內容當資料不當指令（11/16 課）。沒有哪一層是萬能的，重點是每一層擋住其他層漏掉的。

# sandbox_check.py：檢查 settings.json 的沙箱設定（本環境實際執行過）
import json, sys
s = json.load(open(sys.argv[1])).get("sandbox", {})
fs, net = s.get("filesystem", {}), s.get("network", {})
def chk(ok, msg): print(("OK  " if ok else "注意 ") + msg)
chk(s.get("enabled") is True, "sandbox.enabled 為 true（預設是關的）")
chk(s.get("allowUnsandboxedCommands") is False, "allowUnsandboxedCommands=false：關掉『沙箱外重試』逃生口")
chk(s.get("failIfUnavailable") is True, "failIfUnavailable=true：沙箱起不來就不要裸跑")
deny = " ".join(fs.get("denyRead", []))
for p in ["~/.ssh", "~/.aws"]:
    chk(p in deny or "~/" in fs.get("denyRead", []), f"denyRead 有擋 {p}（預設讀得到）")
chk("*" not in net.get("allowedDomains", []), "allowedDomains 沒有萬用字元 *")
chk(not s.get("excludedCommands"), f"excludedCommands 為空（目前：{s.get('excludedCommands', [])}）")
