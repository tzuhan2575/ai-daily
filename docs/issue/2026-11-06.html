🚗 研究

NVIDIA Cosmos 3 Nano 開放四個後訓練模型：多相機駕駛影片、可互動的模擬器、機器人雙臂動作預測

Hugging Face 部落格（NVIDIA）・11/5（已讀全文，未跑模型）

我讀了部落格全文。NVIDIA 在 Hugging Face 釋出四個 Cosmos3-Nano 變體：Transfer-Auto（離線生成最多 11 路同步相機含魚眼，可選 RGB 加 LiDAR，可改天氣、光線、時段）、Sim-Auto（Transfer-Auto 的串流蒸餾版，幾步去噪就產出短片段，供互動式 rollout）、Sim-Transfer（以模擬器的深度、分割、邊緣等控制加文字提示，渲染擬真 RGB）、Sim-Bimanual（依動作預測雙臂機器人影片）。授權為 OpenMDW1.1，允許商用與非商用。參數量文中寫 16B，模型卡寫 15B，文章沒解釋差異。文章沒有給任何基準分數。

白話：白話：給自駕與機器人團隊用的『開源世界模擬器』：可以把一段駕駛資料變成不同天氣的版本，或讓模型即時畫出『接下來會看到什麼』。
💡 為什麼重要這是與 CV／機器人感知最貼近的一則：用生成式模擬擴充訓練與測試資料，是降低真實資料蒐集成本的做法。
🎯 對你的影響　👀 值得追蹤
若你有自駕或機器人感知的側專案，Transfer 類模型可當資料增強候選（推測）；Tap Diary 與日報無關。需要 NVIDIA GPU 與 Docker，我目前環境沒有驗證。
▶ 有 GPU 時，只讀模型卡中 Transfer-Auto 的輸入格式與授權條款，記下你的資料能否直接餵進去；沒有 GPU 就略過。
📖 展開完整解析（5 段）

四個模型各做什麼

Transfer-Auto 偏離線資料增強；Sim-Auto 偏閉環互動；Sim-Transfer 是 sim-to-real 的『渲染器』，物理仍由模擬器負責；Sim-Bimanual 是以動作條件預測影片，輸入為 59 個控制值並補到 64。

技術細節

骨幹是 Mixture-of-Transformers，文字與視覺生成網路用注意力配對；在壓縮潛在空間運作，每個潛在步涵蓋 4 張 RGB 幀；訓練分四階段：雙向適配、teacher forcing、一致性蒸餾（每片段四步去噪）、self-forcing。

怎麼取得與需求

檢查點在 Hugging Face 的 cosmos3-examples 集合，程式與範例在 NVIDIA 的 cosmos-framework GitHub。需要 Linux、NVIDIA GPU、Docker 與 NVIDIA Container Toolkit；vLLM-Omni 範例在一張 GB200 上測試，文章說這不是最低記憶體需求。

文章自述的限制

長串流 rollout 的小誤差會累積；Sim-Transfer 不模擬物理；換感測器配置或領域需用自己的資料後訓練；短訓練成功只證明能跑，不代表收斂，需要保留集評估。

沒有的東西

沒有基準分數；Hugging Face 的下載數只代表熱度。以上都是廠商自述，未見第三方驗證。

HF Papers 2611.03852（僅讀摘要）與 Latent Space・11/3–4（轉述）

我只讀了論文摘要頁，沒讀全文。作者用開放權重模型（因為能看到推理過程），在工具結果揭露前，讓壓縮模型把先前助理推理改寫成較短的狀態記錄（保留決定、不確定性與預定動作），再比較兩種歷史下的後續生成。六條模型路徑中，172 組可比較續寫有 151 組（87.8%）推理較短，各路徑中位數約少 20% 到 50%；成功率變動小但因模型而異。在 SWE-bench Verified Mini（50 題）上，八種壓縮配置有六種總成本較低、七種縮短請求時間，但計入改寫成本後只有兩種縮短請求時間，品質依目標與壓縮模型而異。作者承認任務窄、保真檢查由模型執行。另外 Latent Space 轉述 NVIDIA 的上下文壓縮結果：每次行動一個上下文時 SWE-bench Verified 70.2，對完整歷史 70.0，中位尖峰上下文由 32K 降到 8K（我沒讀原文）。

📘 今日一課 · 12 分鐘

開放權重 vs 閉源：怎麼選、看哪些數字

為什麼今天學這個

今天電子報同時出現 Kimi、Ripple、Hy4、Axion 等開放權重模型，剛好銜接第 3 週「評測與選型」的最後一題。以下為一般概念，我沒有實際下載或執行任何模型；今天的模型數字都是電子報轉述。

是什麼

閉源（API）模型你只能呼叫，看不到權重；開放權重模型你能下載權重自己跑或微調。『開放權重』不等於『開源』：授權、訓練資料、訓練程式不一定公開，要看各模型的授權條款。

為什麼要選

兩者差在四件事：成本結構（按 token 付費 vs 買或租 GPU）、隱私（資料是否離開你的機器）、可控性（能否微調、固定版本不被供應商更新）、品質與維運負擔（閉源常領先，開放模型要自己維運）。

怎麼讀大小數字

『總參數』決定權重要多少記憶體，『活躍參數』（MoE 才有）決定每個 token 的算力。今天的例子：Kimi 2.8T 總／104B 活躍，記憶體需求遠大於 65B dense 的 Ripple，但每 token 計算量級不同（概念推論，未實測）。量化可減少記憶體，第 1 週教過。

怎麼選

先寫下需求：延遲上限、每月呼叫量、資料能否外送、需要的能力。再用『你自己的 20 題』測，而不是只看榜單；榜單分數差零點幾分通常不足以決定。成本要把 GPU、維運與閒置算進去。

10 分鐘小實作

寫一張選型表：列出你的一個實際任務，欄位為『閉源 API／開放權重』，各填成本估算、隱私、延遲、維運負擔，最後寫一句結論。

動手做（勾選記錄進度）

貼給 Claude Code 的指令

請用繁體中文幫我做模型選型表。先問我：任務是什麼、延遲上限、每月呼叫量、資料能否離開本機、預算。然後產生一個 Markdown 表格比較『閉源 API』與『開放權重自行部署』在成本、隱私、延遲、維運、品質風險五個面向，所有價格與規格都請標明『需要我自己查證』，不要編造任何模型名稱、價格或基準數字；最後給一個建議與反例條件。
