Anthropic 推出自架版 Claude Managed Agents（私人測試）：harness、沙箱、憑證、對話紀錄全部放在自己的雲或機房

Claude 官方文章（已讀全文）・11/12；TLDR AI・11/13

Anthropic 11/12 宣布 self-hosted Claude Managed Agents 進入 private beta。Managed Agents 原本是 Anthropic 代管的一組 API，提供 agent harness（主迴圈）、沙箱、憑證處理與 session 歷史；之前已經可以只把沙箱放在自己環境，這次是整個服務都能自架：你自己營運 Managed Agents 伺服器、它的資料庫，以及跑 shell 與檔案工具的 worker。模型請求可以送到 Anthropic、雲端供應商（Amazon Bedrock、Google 的 Agent Platform、Microsoft Foundry）或你自己的 gateway；開發者用的核心 API 和代管版相同。Session 歷史存在你自己的資料庫；若組織和 Anthropic 有零資料保留（ZDR）協議，送給 Claude 的請求比照一般 Messages API 適用。申請方式是聯絡 Anthropic 業務窗口。

白話：白話：以前要用 Anthropic 的『代管 agent 平台』，agent 的大腦和記錄放在 Anthropic 那邊；現在公司可以把整套搬回自己機房，只有『問模型』這一步往外送，而且送去哪裡也自己選。
💡 為什麼重要你在做個人 AI 助理，這篇文章其實是一份『安全的 agent 架構』官方清單：大腦和手分開、憑證不進沙箱、網路白名單、每一步留紀錄。就算你不會申請這個企業版 beta，這四條原則也能直接套在自己的助理上。
🎯 對你的影響　👀 值得追蹤
（推測）你是個人開發者，企業版 beta 大概用不到；但四條安全原則可以直接拿來檢查你的個人助理。
▶ 打開你個人助理的設定，列出：API 金鑰放在哪、agent 能連哪些網域、有沒有逐步紀錄。缺哪一條就先補哪一條，例如把金鑰從程式能直接讀的檔案搬到只有 proxy 能讀的位置。

我讀到什麼

讀了 claude.com 上的官方文章全文（約 5 分鐘長度）。文章最後連到的技術文件我沒讀，所以 API 細節、部署需求（例如資料庫種類、容器規格）、價格都不清楚。這是 private beta，官方沒公布開放日期。

原則一：大腦和手分開

harness（大腦）負責呼叫 Claude，沙箱（手）負責執行 agent 的程式碼，兩者刻意分離：agent 迴圈、session 歷史與 vault 裡的密鑰都在沙箱外。好處是 agent 不依賴某個沙箱一路存活，需要工具時才啟動沙箱，歷史則是沙箱外的事件紀錄（event log）。

原則二：憑證不進沙箱

對 MCP 工具與支援的 API 呼叫，由沙箱外的 proxy 在請求上加憑證，所以沙箱裡的程式碼拿不到原始密鑰。自架版還能接你自己的 secrets manager。這和你在 Claude Code 裡把 token 放環境變數、讓 agent 直接讀到，是不同等級的隔離。

原則三、四：網路白名單與完整紀錄

每個環境可以設允許的主機清單，其他主機一律擋掉；官方舉例修 build 的 agent 只需要 git 主機和套件倉庫。每一步工具呼叫與回傳都會記錄，並以 OpenTelemetry 匯出，可以接進既有的監控系統。

為什麼現在推

官方的說法是 agent 越來越常無人看管地做關鍵工作（修 build、測 release、處理告警、清 bug backlog），需要碰內部系統；有些團隊要求整個服務留在自己環境，以前只能自己造平台。這是官方敘述，沒有客戶名單或數據。

觀察點

（推測）這和前幾期提到的 Perplexity 沙箱逃脫實驗、AWS 本地模擬器屬於同一股潮流：agent 能力上來後，重點轉到『怎麼圈住它』。之後值得看技術文件裡 worker 的隔離方式，以及第三方安全研究對這套架構的評估；目前我沒看到。

llama.cpp 與 ggml 發布 v1.0.0：開始用語意化版本，API／ABI 不相容就升主版號

Hugging Face 官方部落格（ggml-org 團隊，已讀全文；留言只看到前幾則）・11/13

llama.cpp 團隊 11/13 在 Hugging Face 部落格宣布函式庫 v1.0.0：libllama（llama.cpp v1.0.0，公開標頭在 llama.cpp/include/）與 libggml（ggml v1.0.0，標頭在 ggml/include/）。之後所有 ggml-org 專案採用語意化版本：./include 裡的公開 C API 有破壞性變更就升 MAJOR；向下相容的新功能、後端更新、新模型支援或 API 新增升 MINOR；不改 API 的 bug 修正升 PATCH。發布管道列出預先建置檔（Linux、macOS、Windows、Android、iOS）、Docker、Debian、Homebrew、conda-forge、MacPorts、Winget 與 XCFramework（iOS、macOS）。官方說目前支援超過 150 種模型架構變體與所有主流 speculative decoding 方法。

白話：白話：llama.cpp 是讓你在筆電、手機上跑大型語言模型的熱門開源引擎。以前它改得很快、介面常變，接它的程式容易被更新弄壞；現在宣布『1.0』，承諾從此只要會弄壞你的改動，版本號第一個數字就會跳，看版號就知道能不能放心升級。
💡 為什麼重要這週學習進度是『本地跑小模型』，前幾天的課都用 llama.cpp。若你之後想在 Tap Diary（Flutter）或個人助理裡嵌入本地模型，穩定的 C API 與 Android／iOS 預建檔就是能不能長期維護的關鍵。
🎯 對你的影響　🔧 可立即用
你這週在學本地推論，之後專案若依賴 llama.cpp，就能用版號範圍保護自己不被破壞性更新弄壞。

我讀到什麼

讀了官方部落格全文；文中連到的發行說明討論串、後端清單頁面我沒讀，所以不知道 v1.0.0 實際 API 有哪些變動，也不知道舊版號如何對應。留言區只看到幾則歡呼，沒有技術討論。

為什麼要 1.0

官方說專案 3.5 年來長大很多，許多下游應用依賴它的函式庫介面，『有彈性但穩定的 API 至關重要』；之後會更嚴格地讓相容性邊界對下游可見。對使用者來說，最大的改變是可以用版號規則來釘依賴，不用每次升級都賭一把。

API 和 ABI 差在哪

文章說 API 與 ABI 不相容都會反映在主版號。API 是原始碼層的介面（函式名稱、參數），ABI 是編譯後二進位層的介面（結構大小、呼叫方式）。ABI 變了，就算原始碼不用改，舊的編譯產物也可能和新的 .so／.dylib 搭不起來，所以動態連結的 App 特別在意。

分發與 CI

新增或列出的管道包含 Homebrew、Winget、conda-forge、Debian 與 iOS／macOS 的 XCFramework。CI 方面，官方說靠 HF Buckets、HF Jobs 擴充容量，並有 NVIDIA、AMD、Qualcomm、Arm、IBM、Intel 提供硬體跑自架 runner。關於 AI 寫程式，團隊說會『審慎合理地』把 LLM 納入開發流程，但維持程式碼品質、掌控架構與理解實作細節仍是首要。

觀察點

（推測）v1 之後的 MINOR 版會很頻繁（新模型支援也算 MINOR），所以『釘主版號、允許次版號浮動』在這個專案是合理策略。值得觀察第一次 2.0 會因為什麼而升，以及 Ollama、LM Studio 等下游何時跟進新的版號規則；我沒看到它們的回應。

Perplexity 官方部落格（已讀開頭的訓練段與後段的評測、用途；中段文字分類基準未讀，圖表未看）・11/12；TLDR AI・11/13；HN（只看標題與 78 分、17 則留言）

Perplexity 11/12 發布決策模型 Decider v1.3 與蒸餾版 Decider Flash v1.3，權重以 Apache 授權放在 Hugging Face，也可經 OpenRouter 與 Perplexity Decisions API 使用。大模型基於 Qwen3.8-27B，小模型基於 Qwen3.5-4B，以 KL 散度向大模型蒸餾。新功能 locate 會從輸入中抽出符合描述的原文與字元位置，用於命名實體、個資辨識、抽取式問答。官方數字：72 個檢索任務零樣本重排序平均 nDCG@10 83.99，比 Qwen3-Reranker-8B 高 1.81；8 種語言（含中文）多語分類平均準確率 88.16%（Flash 86.50%，Jev 1.14 85.41%）；17 個抽取任務平均 69.0（Flash 63.6，Liquid d1 43.3）；選項重排或改名時答案翻轉率 0.27%，Jev 1.14 為 2.69%–4.84%。全為官方自評。

怎麼把 LLM 改成分類器

每個請求是『一段共用內容（state）＋多個問題』，每個選項配一個標籤 token（A、B、C），在特殊的 <|marker|> 位置用一個線性『決策頭』把隱藏狀態轉成選項分數。決策頭從原模型的輸出層初始化，只保留選項 token 那幾列。v1.3 把骨幹的 full-attention 層改成雙向注意力，並選擇『問題彼此隔離』的模式：每個問題只看 state 和自己，答案更穩定。

訓練三階段

先用大量通用資料全參數微調（刻意排除基準的訓練切分），再用 LoRA 補特定領域，最後用 LoRA 補視覺；LoRA 合併時加權，以保住 held-out 表現。文字階段取三個不同亂數種子的權重平均。小模型用大模型的機率分布當答案做蒸餾，官方說比直接用標準答案訓練更能泛化。

真實流量評測

官方抽了 Decisions API 上線前 18 天、一百萬筆去重且遮蔽個資的請求（約 232 萬個問題），用前沿 LLM 當裁判產生參考答案：Decider v1.3 與裁判一致率 93.98%，v1.2 93.68%，Jev 1.14 93.35%。用 LLM 當裁判本身就有偏差，差距也不大，要保守看。成本比較圖官方自己註明是本機執行、硬體成本計算方式未說明、也沒有對齊延遲。

Perplexity 自己怎麼用

安全規則自我改進：規則引擎即時監控 agent，Decider 離線抽查紀錄找漏報與誤報，一天讀 10 億 token、7,000 個 session，產生 14 個規則修正、6 個在兩天內上線，最忙那條規則的量減少 52%。另外用在監看 RL rollout 失敗原因、爬蟲網頁品質過濾。官方建議：回傳的是機率，門檻要用你自己的小型標註集調。

觀察點

Decider 的設計明確受到 TypeSafe AI 的 Jev 啟發，這個『決策模型』類別一週內出現 Google、Perplexity 多家。還沒有獨立第三方基準；中文只是 8 種語言之一，繁體中文表現官方沒有單獨報告。

🔍 硬體

從公開權重找出晶片指紋：研究稱 DeepSeek、Kimi、MiniMax、螞蟻的六個新模型是在出口管制的 Blackwell 上建立

Unemployment Labs 報告（已讀摘要、主要發現與規模估算；方法細節與附錄未讀）・11/12；TLDR AI・11/13

研究機構 Unemployment Labs 11/12 發布報告，宣稱只靠公開的模型權重，就能還原初始化時留下的數值痕跡，再反推產生這些權重的硬體配置。結論：2026 年 4 月以來 DeepSeek-V4-Flash、DeepSeek-V4-Pro、Kimi K3、Kimi K3.1-Pro、MiniMax-M3、Ling-3.1-flash 六個模型符合 NVIDIA Blackwell（B200／B300 為 148 個 SM，GB200／GB300 為 152 個 SM）；同公司較早的模型符合 Hopper。Qwen、GLM、騰訊、小米、階躍的最新模型仍讀為 Hopper；美團 LongCat-2.0 沒有 NVIDIA 指紋。方法在 24 個公開硬體的模型上全部對中，最強的巧合配對約 8 sigma，六個模型的證據在 49 到 1,385 sigma。報告明說：這只證明能接觸到這些晶片，不證明晶片在哪、怎麼取得、是否違反出口管制。

白話：白話：模型訓練一開始會用亂數填滿權重，而不同 GPU 的核心數量會讓這些亂數的排列方式留下獨特痕跡，就像子彈上的膛線。研究者從公開下載的模型裡找到這種痕跡，比對出是哪一代晶片做的。
💡 為什麼重要這是本期唯一的硬體則。對你的直接影響不大，但『從權重本身推回訓練環境』這種鑑識手法很有意思；而且你若用 DeepSeek、Kimi 等開放權重模型，未來可能受出口管制或採購政策的連帶影響（推測）。

我讀到什麼

讀了報告的執行摘要、主要發現、表 1 與表 2（規模估算）；『我們的調查』之後的方法細節與附錄沒讀，所以無法說明他們如何從權重還原初始值，也無法自己判斷方法可靠度。作者單位與經費來源我沒查。

驗證方式

報告說對 DeepSeek-V4-Flash 與 Kimi K3 還在實體 Blackwell 上重現確認；唯一想到的替代解釋是特殊配置的 AMD 硬體（同樣受出口限制），對 V4-Flash 已排除、對其他五個認為很不可能。NVIDIA 自家 Nemotron-3 Ultra（技術報告寫用了 GB200）讀出 152 SM，與 Kimi K3 相同。

訓練規模估算

以『每個活躍參數每個 token 約 6 次運算』加注意力、GPU 約 20% 峰值效率推估：Kimi K3 約 4,500 張 Blackwell、DeepSeek-V4-Pro 約 3,000 張，各跑兩三個月；五個訓練合計約 12,000 張，約等於 30,000 張 H100。用每張約 7 萬美元換算，最大叢集約 2 到 3 億美元。報告自己說對這些估計『沒有信心』，因為效率、token 數、訓練天數都是假設，天數減半 GPU 數就加倍；11/12 已修正過一次（原本估 2,000 到 3,000 張）。

限制與爭議

指紋只說明『權重是在 Blackwell 上建立的』，報告用『支持但不證明』來形容『訓練也在 Blackwell 上進行』。晶片可能在海外資料中心租用；報告引用 WSJ 說 ByteDance 在馬來西亞部署約 36,000 張 Blackwell，但那是另一家公司、另一件事。目前我沒看到相關公司回應。

觀察點

（推測）若方法被廣泛接受，開放權重本身就可能成為出口管制執法的證據來源，實驗室可能開始在初始化上做手腳以隱藏指紋。之後可看美國商務部或 NVIDIA 是否回應，以及其他研究者能否獨立重現。

NVIDIA 示範 SimReady 資產＋agent skills：在 Isaac Sim 6.2 用自然語言組裝 UR17G 手臂與夾爪、完成抓罐子任務

Hugging Face 部落格（NVIDIA 撰寫，已讀全文文字，影片與圖片沒看）・11/13

NVIDIA 11/13 在 Hugging Face 發表教學：從 Hugging Face 上的開放資產庫 SimReady Central 下載 UR17G 機械手臂、Robotiq 2F-140 夾爪與飲料罐三個 OpenUSD 資產，在 Isaac Sim 6.2 組成場景，並讓 coding agent（文中用 GPT-6 Sol，官方說其他能載入 skills 並對 Isaac Sim 執行 Python 的 agent 也可能可行）透過 Isaac Sim 內建的 Agent Skills 組裝手臂與夾爪、驗證物理設定、產生抓取放置的控制程式。Isaac Sim 以 ./isaac-sim.sh --enable isaacsim.code_editor.python_server 啟動，讓 agent 能遠端送 Python 進去。用到的 skills 名稱包括 isaac-sim-remote、usd-articulation、manipulaiton-ik（原文拼法）、physics-simulation。

白話：白話：『SimReady』是指 3D 模型不只長得像，還已經填好碰撞外形、重量、關節與馬達設定，丟進模擬器就能動。這篇示範用聊天的方式叫 AI 幫你把手臂裝上夾爪，再寫程式去夾一罐飲料搬到目標點。
💡 為什麼重要你是機器人感知背景，模擬環境搭建一向很花時間。『資產附驗證報告＋agent 透過 skills 操作模擬器』這個組合，跟你用 Claude Code＋自己的 skills 是同一種工作方式，搬到機器人領域。

SimReady 規格的三層

SimReady Foundation 把需求分成三層：Profile（一個用途需要的一組特性，例如機器人本體）、Features（例如可控制的關節）、Requirements（每個特性要檢查的設定，例如關節驅動參數）。文中手臂驗證報告用 Robot-Body 4.0.0、夾爪用 Robot-Gripper 3.0.0，兩者都通過 PhysX 驅動關節檢查。

執行前要檢查什麼

官方提醒：模型靜止時看起來正確，不代表動起來正確。要先檢查關節極限與驅動設定、試一個小動作與開合夾爪、確認罐子放在桌面上不會穿過去；執行時觀察移動中罐子是否一直留在夾爪裡。

示範的簡化假設

文章很誠實地列出限制：罐子起始位置固定、沒用視覺、碰撞檢查有限；不模擬罐子變形與液體晃動；水平抓取的驅動力上限 2 N·m 是模擬中試出來的，不是依原廠指尖力規格；沿固定路徑點移動、不重新規劃。官方明說結果不代表對位置不確定、不同負重或真實硬體的穩健性。

語意化版本與釘版本：本地推論依賴怎麼升級才不會壞

為什麼今天學這個

今天 llama.cpp 與 ggml 宣布 v1.0.0 並採用語意化版本，這直接銜接第 4 週『本地跑小模型』的『本地推論工具』主題：前幾天學了怎麼跑 llama-server，今天學怎麼長期維護這個依賴。版號規則出自 llama.cpp 官方部落格；練習裡的 Python packaging 程式碼我在這個環境實際跑過（packaging 24.0），llama.cpp 本身這裡沒有安裝，相關指令未實際執行。

是什麼

語意化版本（Semantic Versioning，簡稱 SemVer）把版號寫成三段：主版號.次版號.修補版號，例如 1.4.2。llama.cpp 官方今天公布的規則是：公開 C API（./include 裡的標頭）有破壞性變更就升主版號；向下相容的新功能、後端更新、新模型支援或新增 API 升次版號；不改 API 的 bug 修正升修補版號。

為什麼重要

你的程式依賴別人的函式庫，對方一更新，你的程式可能就壞了。有了 SemVer，版號本身就是一份承諾：從 1.4 升到 1.9 應該不用改程式；從 1.x 升到 2.0 就要預期得改。你可以讓工具自動接收安全的更新，只在主版號變動時停下來人工檢查。

怎麼運作：版本範圍

套件管理工具用『範圍』描述能接受的版本。常見寫法：>=1.0.0,<2.0.0 表示 1.x 都可以、2.0 不行；Python 的 ~=1.0.0 表示只接受 1.0.x 的修補版。範圍太寬會被破壞性更新打到，太窄（完全釘死 ==1.0.0）則收不到 bug 修正。llama.cpp 新模型支援會落在次版號，若想跟上新模型，釘在主版號就好。

API 和 ABI

llama.cpp 官方說 API 與 ABI 不相容都會升主版號。API 不相容：你得改原始碼才編得過。ABI 不相容：原始碼不用改，但舊的編譯產物配新的動態函式庫（.so、.dylib）可能出錯，所以要重新編譯。若你在 App 裡打包靜態連結的函式庫，ABI 問題比較少；若用系統安裝的共享函式庫，就特別要注意。

實務做法

第一，記錄你實際用的版本與安裝管道（官方列出 Homebrew、Docker、conda-forge、Winget、預建檔等）。第二，在依賴設定寫範圍而不是什麼都不寫。第三，用鎖定檔（lock file）記錄實際安裝的確切版本，讓每次建置可重現。第四，主版號升級時先讀發行說明，在分支上測過再合併。

動手做（勾選記錄進度）

範例檔案

from packaging.specifiers import SpecifierSet
from packaging.version import Version
s = SpecifierSet('>=1.0.0,<2.0.0')
for v in ['0.9.0', '1.0.0', '1.4.2', '2.0.0']:
    print(v, Version(v) in s)
# 實際輸出：0.9.0 False / 1.0.0 True / 1.4.2 True / 2.0.0 False

貼給 Claude Code 的指令

請用繁體中文帶我練習語意化版本。1) 用 Python 的 packaging 套件寫一個小腳本 semver_check.py：輸入一個版本範圍（例如 >=1.0.0,<2.0.0 或 ~=1.0.0）和一串版本號，印出每個版本是否符合；實際執行並貼出輸出。2) 檢查我這台機器上有沒有 llama.cpp（試 which llama-server、brew info llama.cpp，或我 ~/llm-lab 裡的建置），回報實際版本與安裝方式；找不到就直接說找不到，不要猜。3) 讀 llama.cpp 官方 v1.0.0 公告（Hugging Face 部落格 ggml-org/llama-cpp-v1）裡的版號規則，幫我在 ~/llm-lab/README.md 加一段『依賴與升級規則』。每個指令都要實際執行，失敗就說明原因，不要編造版本號。
