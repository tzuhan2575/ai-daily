🔁 模型發布

智譜 Z.ai 發布 GLM-5.4：第一個『迴圈 Transformer』旗艦，把 GLM-5 的 28 層重複跑兩次，官方稱達到 2 兆到 3 兆參數模型的水準；權重『安全強化後』才開源

Z.ai 官方部落格〈GLM-5.4: Toward Generalized Coding with Our First Loop Transformer〉（已讀全文文字；評測表與示範影片是圖片／影片，沒看）＋HN 討論（1,009 分、329 則留言，讀了前 12 則頂層留言）・11/23

Z.ai 11/23 發布 GLM-5.4。做法：拿已預訓練好的 750B 參數 GLM-5 基礎模型，把其中 28 層改成『共用權重、跑兩次』的迴圈，再繼續訓練，而不是從頭訓練。三個關鍵改動：① 每一圈有各自的逐 token『閘門』，控制要把多少更新寫回主幹，避免數值越跑越大；② 第二圈重用第一圈的稀疏 KV cache，只另外保留一個滑動視窗的新 KV，所以多跑一圈只多一個視窗的記憶體，而不是整份上下文；③ 第二圈直接沿用第一圈稀疏注意力挑好的索引。官方說在 1B、4B、30B、750B 逐級驗證，30B 版本在『參數完全相同、訓練算力只多約 10%』的對照下明顯進步，數學、科學推理與長上下文進步最多，GPQA-Diamond、MMLU-Pro 等的平均輸出長度少 10–14%。速度：離峰最高 200 token／秒、尖峰 70–80 token／秒。目前可在 GLM Coding Plan、ZCode、Z.ai Chat 使用，API『即將推出』，權重『完成必要的安全強化後』開源。官方自承缺點：容易陷入過長的『馬拉松式思考』。

白話：白話：一般模型每一層只算一次；迴圈 Transformer 是讓中間一段層『再算一遍』，像把草稿再讀一次修改。參數數量不變、模型檔不會變大，但每個 token 花的運算變多，等於用『想得更深』換『記得更多』。智譜的主張是：寫大型程式、做資安、3D 建模這種一長串推理的工作，靠的是運算深度，而不是把參數堆更大。
💡 為什麼重要這是 11/21 Inkling 2 Mini『中間層繞三圈』之後，第二個主打迴圈架構的知名模型，而且是旗艦等級——『迴圈』正在變成開放模型陣營的共同方向。你如果在 Claude Code 之外也會試 GLM 系列，要知道它現在沒有公開分數可比，而且容易想太久。
🎯 對你的影響　👀 值得追蹤
目前只能在智譜自家方案與聊天介面用，API 還沒上線、權重沒開，也沒有公開分數；對你的 Claude Code 日常沒有立即影響。迴圈架構會讓『同參數量、不同延遲』成為常態，之後選本地模型時不能只看參數數字（推測）。
▶ 在你的模型筆記裡新增一欄『是否迴圈／每 token 實際運算量』，把 GLM-5.4 與 Inkling 2 Mini 填進去，等 GLM-5.4 API 上線後再用你自己的 eval（11/8 那課）測一次。

我讀到什麼

部落格是用 JavaScript 動態產生的頁面，我從頁面程式裡取出全文文字；30B 對照實驗的分數表、四段示範影片（自己旁白的 MV、在 FreeCAD 建六軸機械手臂、做完整遊戲、GLSL 寫的 3D 賞鳥場景）都是圖片或影片，我沒看到內容。所以下面只寫文字明講的數字。官方沒有在文字裡給 750B 正式版的任何 benchmark 分數，『相當於 2T–3T 參數模型』是官方說法，沒有第三方驗證。

為什麼不從頭訓練迴圈模型

文章自己交代了學術脈絡：2018 年 Universal Transformer 就提出權重共用的深度，近年的 recurrent depth、looped LM 在小規模有成效；但從頭訓練的迴圈模型，在相同預訓練算力下仍輸給不共用權重的模型。智譜的解法是『改裝』既有的預訓練模型再繼續訓練，用相對小的額外算力拉高上限。這和 11/23 我們介紹的『模型改寫自己權重』研究一樣，都是在已有權重上做文章的路線。

閘門學到的分工

官方描述訓練後閘門出現明顯分工：第一圈負責建立全域上下文、寫回時很保守（閘門值小）以維持數值穩定；第二圈重用這個狀態來精修輸出、閘門全開。閘門還會依 token 難度調整：難的 token 第一圈就寫得比較多。這是官方對內部行為的解讀，沒有附可驗證的分析資料（或在我沒看到的圖裡）。

記憶體帳怎麼算

迴圈最直接的成本是 KV cache：天真做法每一圈都存一份完整 KV，跑兩圈記憶體就兩倍。GLM-5.4 讓第二圈共用第一圈挑出的稀疏 KV，自己只多存一個滑動視窗，官方說在 100 萬 token 上下文時，部署成本比 GLM-5.3 的增加『在可控範圍』（沒有給具體數字）。這和第 1 週學過的 KV cache 是同一件事：上下文越長，KV 越是瓶頸。

社群反應

HN 前排留言最集中的抱怨是『沒有 benchmark 分數』——有人猜分數不夠亮眼才不放，也有人說唯一的能力資訊是 30B 未完整後訓練版的那張表。另一類是實際使用心得：有人說中國模型的『馬拉松思考』在簡單任務也一直自我懷疑，完成時間比前沿模型長很多。也有人擔心迴圈把推理移進看不見的隱藏狀態（社群叫 neuralese），會讓思考過程更難被人讀懂與監控。這些是留言意見，不是驗證結果。

觀察點

① API 上線後的第三方評測（尤其 SWE 類與長任務）；② 權重何時、以什麼授權開放；③ 官方說『下一個明顯更大的模型很快就好』；④ 官方提到的下一步是『自適應運算』——難的 token 自動多跑幾圈，這會讓延遲和成本更難預估。

🛡️ 資安

OpenAI 與 Cisco 開源 Shirudo：用 eBPF 在 Linux 上掛『臨時盾牌』擋漏洞利用、服務不用重啟；示範中由 Codex 產生的盾牌擋下對執行中 Elasticsearch 的 Java4Shell 攻擊

OpenAI 官方文章〈OpenAI and Cisco introduce Shirudo〉（已讀全文文字；架構圖、技術演示影片、GitHub 程式碼與文件沒讀）・11/23

OpenAI 與 Cisco 11/23 推出開源執行環境 Shirudo（日文『盾』）。問題設定：修補程式從測試到部署常要幾天到幾週，這段時間漏洞還開著，而攻擊和正常請求常用到同一個 Linux 操作，整個擋掉服務就掛了。Shirudo 讓團隊做一個針對性的『shield』（盾牌），先觀察它會不會誤擋正常流量，經營運人員核准後才在服務不停機的情況下上線。四個設計：① 即時防護：eBPF 程式擋住有漏洞的程式路徑，不必重開機；② 給 agent 可程式化的控制介面，讓它調查漏洞、寫盾牌、對真實流量驗證，但部署權在人；③ 盾牌要密碼學簽章、載入前驗證，並經 Linux 的 eBPF verifier 檢查；④ 用 TPM 留下『哪些防護何時被載入或移除』的可驗證紀錄。官方示範：用 Codex 產生一個盾牌，在 Java 的 Base64 解碼器加上輸入檢查，直接掛到執行中的 Elasticsearch 程序，惡意輸入被拒、服務照跑。授權為 BSD 2-Clause，BPF 程式採 BSD／GPL 雙授權；12/15 有技術網路研討會。

白話：白話：eBPF 是 Linux 讓你在核心裡安全地插入小程式的機制，可以在『某個函式被呼叫時』先檢查一下。Shirudo 就是用它在漏洞出現的那一點加一道檢查，像在破洞上先貼一塊膠布，等正式補丁做好再撕掉。新的地方是：寫這塊膠布的可以是 AI agent，但貼不貼由人決定，而且每次貼上撕下都有硬體背書的紀錄。
💡 為什麼重要這是第 5 週『Agent 安全與權限』的實際案例：agent 能寫防護，但部署要經人核准、要簽章、要留紀錄——正是『不可逆操作的確認閘門』那一課的設計。你目前沒有在管 Linux 伺服器艦隊，所以實際用到的機會不大。

我讀到什麼

讀了 OpenAI 官方文章全文文字。文中連到的 Linux Plumbers Conference 技術演示、VM quickstart、Isovalent 自學實驗室、GitHub repo 與文件我都沒讀，所以不知道盾牌實際怎麼寫、支援哪些核心版本、效能開銷多少。『Codex 產生的盾牌擋下攻擊』是官方在『受控測試』下的結果，沒有第三方重現。

為什麼需要『臨時盾牌』

文章的核心論點是：找到漏洞不等於明天就能修好所有系統。修補要測試、排程、重啟，關鍵服務不能隨便停；而直接用防火牆或權限擋掉某個系統呼叫，又常常連正常功能一起擋掉。eBPF 的好處是可以掛在很精準的位置（例如某個函式的輸入）只擋特定模式，而且掛上、拿下都不用重開機。

人在哪一步

官方特別強調『Security teams control what gets deployed』：agent 可以調查、寫盾牌、拿 exploit 和真實流量測，但上線需要營運人員核准；盾牌有簽章、載入前驗證，TPM 留下載入與移除紀錄。這和 11/17 那課講的 PreToolUse 確認閘門、以及 11/19 那課『agent 能碰什麼要先定義』是同一套思路，只是對象從你的筆電換成伺服器核心。

長期目標

官方說想要的是：漏洞揭露時同時附上測過的盾牌，讓營運者可以先評估部署；應用程式只拿到需要的權限，政策由系統自動產生與維護；被入侵時能把服務恢復到經驗證的已知良好狀態。這些都是規劃，不是已完成的功能。

沒有回答的問題

文章沒有談：盾牌寫錯造成誤擋時怎麼快速回滾的實際流程、對效能的影響、和既有 eBPF 安全工具（例如 Isovalent 的產品，Isovalent 已屬 Cisco）的關係與差異。我沒看留言或第三方評論，社群反應不明。

🗜️ 工具

NariQ 把 Qwen3.8-27B 壓到 10 GB：3-bit 版在 DeepSWE、Terminal-Bench 與 BF16 原版打平（官方用 Claude Code 驅動測量）；但要用作者自己的 llama.cpp 分支，Mac 每秒不到 4 個 token

Hugging Face 模型卡 nari-labs/Qwen3.8-27B-NariQ-GGUF（已讀全文文字與表格，三張圖沒看；技術報告 arXiv 2611.26157 沒讀）＋HN 討論（102 分、18 則留言，讀了前 10 則頂層留言）・11/20 發布，HN 11/23

Nari Labs 11/20 釋出 Qwen3.8-27B 的 NariQ v1 GGUF，有 3、2.5、2 bits per weight 三種，檔案 10.12、8.44、6.75 GB（原本 BF16 為 53.8 GB），另有 0.93 GB 的 BF16 視覺投影檔（mmproj）三種共用。官方表格：DeepSWE（113 題×3 輪，平均 pass@1）BF16 39.8%、3-bit 41.0%、2.5-bit 41.9%、2-bit 28.6%；Terminal-Bench 2.1（82 題×3）62.6% / 63.8% / 60.2% / 52.4%；AIME 25+26：97.7 / 98.3 / 96.5 / 86.0；看圖的 RealWorldQA：82.4 / 82.4 / 81.3 / 80.9。agent 評測用 Claude Code CLI 2.1.309（thinking 開、effort max）驅動本地模型、262,144 token 上下文。方法是 trellis-coded 訓練後量化（PTQ），用真實的 coding agent 執行紀錄做校準。24 GB 顯卡 3-bit 版可放約 135K 上下文，全 262K 上下文約需 30 GB。

白話：白話：量化就是把每個權重用更少的位元存（第 1 週學過）。一般認為壓到 3 bit 以下會明顯變笨；NariQ 的說法是，只要校準時用的是『模型真的在做 agent 任務時的資料』，3-bit 和原版在長任務上分不出差別。代價是檔案格式是新的，現在只有作者自己的 llama.cpp 分支讀得懂。
💡 為什麼重要這直接延續第 4 週『本地跑小模型』與 11/15『量化後到底掉多少』那課：它不只給 benchmark，還給了和原版的 KL 散度、三輪平均與逐題計數——正是那課教的『該看什麼』。但它也示範了該警惕的地方：評測工具不同，分數就不能直接比。

我讀到什麼

讀了模型卡全文文字與四張表格（主要分數、檔案大小、可放的上下文、解碼速度）。三張圖（KL 散度對檔案大小、DeepSWE 與 Terminal-Bench 對檔案大小）我沒看，只讀了圖說。技術報告沒讀。所有分數都是 Nari Labs 自己測的，模型卡說作者是一人作業（solo effort），目前沒有第三方重測。

分數怎麼讀

兩個細節值得注意：① 3-bit、2.5-bit 在 DeepSWE 分數『高於』BF16（41.0、41.9 對 39.8），這比較可能是量測雜訊而不是真的變強——三輪平均、113 題，差 1–2 題就會有這種差距；官方另給的『新測試通過比例』是 83.1%（BF16）、82.9%、83.2%、77.2%，更能看出 3-bit、2.5-bit 與原版相當、2-bit 掉了一截。② BF16 第 3 輪有一次驗證逾時被算 0 分，模型卡有明講。

harness 差異的爭議

模型卡把自己的結果和 Unsloth Dynamic V3.1 畫在同一張圖，但特別說明 Unsloth 用 mini-swe-agent、自己用 Claude Code，『請各自和同一 harness 的 BF16 線比較』。HN 有人指出：從圖看，大部分差距來自 harness 而不是量化；也有人說控制組 BF16 在他們的 harness 比 Unsloth 的高出這麼多，反而削弱了比較的說服力。另一位留言者則肯定它做了『held-out 資料、多種長任務』這些他平常想看卻看不到的檢查。還有人認為這個格式是從 exl3 的 trellis codebook 演變來的，模型卡沒有把淵源講清楚。

實際能不能跑

限制寫得很誠實：① 只有作者的 llama.cpp 分支能載入，官方 llama.cpp、Ollama、LM Studio 都還不行；② 分支主要針對 RTX PRO 6000 這類 SM120 顯卡最佳化，Ampere、Ada、Hopper 與 Apple M 系列『目前比同等 GGUF 慢』，Ampere 之前的 GPU 退回 CPU，AMD、Intel GPU 不支援，GeForce 沒測過；③ M3 Pro（18 GB）用 3-bit 檔解碼約 3.8 token／秒；④ 多 token 預測（MTP）模組還沒量化，KV cache 與激活值也還是 BF16。RTX PRO 6000 上 4K 上下文解碼 3-bit 約 88.9 token／秒，比同 GPU 上 Unsloth UD-IQ3_XXS（10.9 GB）的 94.7 略慢。

和今天一課的關係

模型卡特別寫：『視覺塔維持 BF16，只量化語言模型』，視覺部分是一個獨立的 mmproj 檔。為什麼看圖的部分要分開放、為什麼它不大卻不壓——就是今天『VLM 的視覺編碼器』那課要講的。

觀察點

VLM 的視覺編碼器：一張圖怎麼變成模型讀得懂的 token？從 mmproj 檔看起

為什麼今天學這個

第 6 週『把 AI 放進 App』四個主題已於 11/20–11/23 全部上完，今天開始第 7 週『多模態與機器人模型』的第一個主題『VLM 的視覺編碼器』。今天的 NariQ 模型卡特別寫『視覺塔維持 BF16、只量化語言模型』，並另外附一個 0.93 GB 的 mmproj 檔；RoboTrack 那則也在講『模型怎麼看影片畫面』。剛好拿 mmproj 當入口，看懂 VLM 的眼睛長什麼樣。

是什麼

VLM（視覺語言模型）＝『會看圖的語言模型』。它多半由三塊組成：① 視覺編碼器（vision encoder），通常是 ViT（Vision Transformer），把圖切成一格一格的小方塊（patch），每塊變成一個向量；② 投影器（projector），把視覺向量轉成語言模型能接受的寬度，常順便把相鄰幾塊合併，減少數量；③ 語言模型本體，把這些『視覺 token』當成和文字 token 一樣的輸入。所以對語言模型來說，一張圖就是一串額外的 token。

為什麼你要懂這個

三個實際影響：① 成本與上下文：一張圖會吃掉幾十到幾千個 token（第 1 週學過 token 計價與上下文視窗），圖越大、越多張，越快塞滿；② 本地部署：llama.cpp 官方說明多模態需要兩個 GGUF 檔——語言模型本體，加上一個 mmproj（multimodal projector）檔負責圖片編碼與投影；少了它就只能讀文字；③ 量化策略：視覺編碼器通常比語言模型小很多，但對數值精度敏感，所以像 NariQ 這樣只壓語言模型、視覺部分保留 BF16，是常見取捨（『對精度敏感』是一般經驗，我沒有找到針對這個模型的實驗佐證）。

怎麼運作：以 SmolVLM-256M 為例

我實際下載了 ggml-org 的 mmproj-SmolVLM-256M-Instruct-Q8_0.gguf（約 104 MB），用 gguf Python 套件讀它的中繼資料：架構是 clip、投影器類型 idefics3；視覺編碼器 12 層、寬 768、共約 9,350 萬參數；輸入 512×512、patch 大小 16×16，所以一張圖切成 32×32 = 1,024 個 patch；scale_factor 為 4，表示每 4×4 = 16 個相鄰 patch 合併成一個，最後剩 64 個視覺 token，每個 576 維。檔案裡投影層 mm.model.fc.weight 的形狀是 12288×576，而 12288 = 768×16，正好對應『16 個 768 維向量接起來，再投影成 576 維』——這個對應是我從形狀推的。

patch、解析度與 token 數的關係

公式很簡單：patch 數 =（邊長 ÷ patch 大小）²，視覺 token 數 = patch 數 ÷（合併倍數²）。所以解析度加倍，token 數變四倍；合併倍數越大，token 越少但細節損失越多。這解釋了為什麼看小字、看細節的任務（OCR、儀表、遠處小物件）常需要高解析度或把大圖切成多塊（tile）分別編碼——不同模型怎麼切塊差異很大，llama.cpp 官方文件也提醒 OCR 模型有特定的輸入格式，要各自查模型說明，今天的腳本沒有涵蓋切塊。

和你的 CV 背景怎麼接

你熟悉的 CNN 特徵圖，到了 ViT 就是 patch 向量；位置資訊靠位置編碼（這個檔案裡的 v.position_embd.weight 形狀是 768×1024，正好對應 1,024 個 patch 位置）。VLM 的『眼睛』本質上就是一個你很熟的影像骨幹網路，差別在最後接了一個投影器，讓輸出能被語言模型當成文字讀。下一課會講 VLA：再接一個輸出動作的頭，就變成機器人模型。

範例檔案

import sys
from gguf import GGUFReader
r = GGUFReader(sys.argv[1])
g = lambda k: r.fields[k].contents() if k in r.fields else None
img, patch = g("clip.vision.image_size"), g("clip.vision.patch_size")
width, layers = g("clip.vision.embedding_length"), g("clip.vision.block_count")
scale = g("clip.vision.projector.scale_factor") or 1
out_dim = g("clip.vision.projection_dim")
side = img // patch
patches = side * side
tokens = patches // (scale * scale)
params = sum(int(t.n_elements) for t in r.tensors)
print(f"投影器類型 {g('clip.projector_type')}，視覺編碼器 {layers} 層、寬 {width}，共 {params/1e6:.1f}M 參數")
print(f"輸入 {img}x{img}，每塊 {patch}x{patch} 像素 -> {side}x{side} = {patches} 個 patch")
print(f"每 {scale}x{scale} 個 patch 合併成 1 個 -> 每張 {img}x{img} 圖 {tokens} 個視覺 token，每個 {out_dim} 維")
