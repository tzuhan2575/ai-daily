🧭 工具

Gemini Decisions API：不生成文字，只在你給的選項裡打分，輸入每百萬 token 0.10 美元、輸出不收費

Google 官方部落格（已讀全文）・11/11；HN 討論（只看標題與分數 187 分、61 則留言）

Google 11/11 推出 Gemini Decisions API，由新模型 gemini-decision-1 驅動，定位是『快速、封閉式決策』：工具選擇、政策檢查、模型路由、內容分級。單次輸入可含文字、圖片、音訊、影片、PDF，上限 256K token；一次請求最多帶 1,000 個獨立問題，題型三種：是非（回傳條件成立機率）、多選一（2 到 255 個選項，回傳各選項正規化機率）、有序評分（回傳加權連續分數與各級機率），每個答案附 0 到 1 的信心分數。官方說模型不逐 token 生成，而是在單次前向傳遞中替候選選項評分。官方數字：端到端延遲 150 到 250 毫秒、模型運算中位數 50 到 100 毫秒（context 16K token 以內）；成本約為 Gemini 3.5 Flash-Lite 走 Interactions API 的五分之一。定價：輸入每百萬 token 0.10 美元、輸出 0 美元，AI Studio 有免費額度。以上皆為 Google 自己的說法；基準圖表的具體數值文字裡沒有，我無法核對。

白話：白話：一般 LLM 是『寫一段答案』，這個是『考選擇題』。你給它一張圖加十個問題，它一次回你每題的機率與信心。因為不用一個字一個字生成，所以又快又便宜，適合當程式裡的『判斷閘門』。
💡 為什麼重要你做 agent 與個人助理時，常需要『要不要呼叫這個工具』『這個請求該丟給哪個模型』這類判斷，目前多半用完整 LLM 呼叫，慢且貴。這類端點把它變成便宜的函式呼叫；今天的機器人安全論文 LEASH 也提到可用 Decisions API 當閘門。

（推測）與你的個人 AI 助理有關：路由與工具選擇閘門若改用這類端點，可能省延遲與費用；但品質是否夠、邊界案例怎麼處理，只靠官方說法無法判斷。
▶ 先不整合。拿你助理目前『判斷要不要呼叫工具』的 20 筆真實請求，在 AI Studio 免費額度試一次，記下它的信心分數分布與錯判數，再決定要不要取代現有做法。

三種題型

是非題給條件成立與不成立的描述標準；多選題支援 2 到 255 個選項；評分題用從 0 開始的有序量表，回傳加權後的連續分數。每題都有信心分數，方便程式把模糊案例丟給備援流程或人工。

為什麼快

官方說法：單次前向傳遞替候選項打分，不逐 token 生成，所以 1 題到 100 題每次請求延遲幾乎持平（16K token 以內）。256K 的輸入上限與這個延遲數字的條件不同，要分開看。

計費方式

共用的 input 每次請求只算一次，每個問題只額外計算其指令與標準的 token；沒有輸出 token、思考 token、語音轉錄或 OCR 的另外費用。

取得方式

透過 Gemini API 與 AI Studio 的金鑰；官方有 Python、JavaScript、REST 指南，Python 以 google-genai SDK 的 client.decisions.create 呼叫。已列出整合 OpenRouter、LangChain、Vercel、LiteLLM、Pydantic AI；Google Cloud 版『即將推出』。

限制（部分為我的推論）

只能在給定選項中選或評分，不能寫自由文字；官方沒給完整限制清單；Notebook 路由案例『簡單查詢延遲最多降 40%』是內部案例，未經獨立驗證。

✈️ 政策安全

聯合航空宣布禁止第三方 AI 代理代客訂機票，理由是資安、誤操作與聯邦規定

CBS News（已讀全文）・11/11；HN 討論（只看標題與分數 198 分、203 則留言）

美國聯合航空 11/11 宣布，將限制未經授權的第三方個人 AI 代理或助理使用其服務，並更新訂票與開票政策。作法分兩層：直接在自家數位平台封鎖，以及透過旅行社與比價平台間接限制。公司提出三個理由：代理需要旅客的登入與付款憑證，交給第三方有外洩風險；AI 可能造成非預期的消費、帳戶變更或動用里程；由 AI 代辦報到等程序可能違反聯邦規定（例如要求旅客本人確認行李內無違禁物品）。報導沒有提供具體數字。

白話：白話：你請 AI 幫你訂機票，航空公司說『我不接受這種機器人幫你操作我的網站』，要你自己來，或用它認可的比價網站。
💡 為什麼重要你自己在做個人 AI 助理，這是第一線的實例：服務方可能不歡迎『代替使用者操作』的代理。助理要碰的網站，政策隨時可能改，不能假設爬得到、也不能假設用戶授權就夠。
🎯 對你的影響　👀 值得追蹤
與你的個人 AI 助理方向有關（推測）：若助理將來要代你操作第三方網站，會碰到條款與封鎖風險。與 Tap Diary 目前無直接關係。
▶ 在助理的設計筆記中加一條『第三方網站操作前先查其對自動化／代理的條款，優先用官方 API 或授權通道』。

兩層封鎖

一層是自家平台直接擋；另一層是透過旅行社與比價平台間接限制。報導說更新的是訂票與開票政策。

三個理由

憑證外洩、非預期操作（含動用 MileagePlus 里程）、以及可能違反聯邦規定。其中聯邦規定的例子是報到時須由旅客本人確認行李。

分析師的看法

航空業分析師 Henry Harteveldt 認為這顯示聯合想保有訂票流程的控制權，不想在 Google 搜尋、比價網與線上旅行社之外再多一個影響力更大的中介；他也提到 AI 機器人查詢航班會增加航空公司成本。他認為票價仍可在 Kayak、Hopper、Google Flights 等平台買到。

對照

報導提到西南航空採不同策略，讓 ChatGPT 使用者可查看其航班庫存，並透過 AI 應用進入其官網。

觀察點

其他航空與電商是否跟進；『授權代理』在服務條款中會不會有正式的通道；封鎖在技術上怎麼偵測，報導沒有說。

AlphaProof Code：官方稱用約四週證明 Signal 加密協定實作的關鍵安全性質，產出超過 600 萬行 Lean

Google DeepMind 官方部落格（已讀全文）・11/10

DeepMind 11/10 宣布 AlphaProof Code 以形式化驗證證明 Signal 協定實際程式碼的關鍵安全性質（該協定也用於 Google Messages 等）。官方稱這是 AI 首次以此深度驗證廣泛部署的加密協定，也是首次有方法驗證這類協定的實作程式碼。流程：人類專家與多個大型語言模型決定要證明什麼，把安全目標轉成形式化規格並由專家逐一審查；基於 Gemini Carbon 的代理寫證明，產出超過六百萬行 Lean 程式碼；代理先自我審計，標出約 1% 需人工複查，其餘由 Lean 自動檢查。驗證範圍涵蓋編譯後實際在裝置上執行的程式碼。官方數字：約四週，過去專家團隊通常需數年；測試時把兩個已修復的真實漏洞放回隔離版本，系統產生機器可檢查的證明指出該版本不安全。以上為官方說法，我沒有讀技術論文。

白話：白話：Lean 是一種『證明檢查器』，只要證明寫得對它才會放行。AI 寫了超大量的證明，檢查器負責驗，所以就算 AI 會出錯，也不會讓錯的證明過關。
💡 為什麼重要重點不在加密本身，而在模式：『AI 產生、機器檢查』能把 AI 的不確定性關在驗證器外面。你寫的 agent 與 CV 程式也一樣——產出再多，最後要有能自動判對錯的檢查器才可信。

與你目前專案（Tap Diary、日報網站、個人助理）沒有直接關係，形式化驗證也非日常工具。

分工

人決定證明什麼並審規格；代理寫證明；Lean 檢查。規格是否正確仍靠人，這是整個鏈條的信任根。

規模

驗證層級

官方強調驗證的是編譯後在裝置上執行的程式碼，而不只是設計，目的是涵蓋設計與實作的落差。

🦾 研究

Embodied First Exam：讓編碼代理控制 47 種模擬機器人，最強者標準設定成功率僅 34%

Hugging Face Papers 頁面（已讀摘要與前段結果，頁面很長，後 27 萬字未讀）・11/9

論文提出 EFE，評測編碼代理控制模擬機器人：代理可直接輸出動作、寫程式控制，或訓練策略再控制。共 1,156 個任務、35 個套件、47 台機器人（9 個套件新建，26 個改編自既有基準）。每個任務有三種設定：Standard（只能由感測器觀測、預設不可重置）、Realtime（模擬持續運行）、Privileged（可取得完整狀態並無限重置，用來估上限）。核心集 456 題中，表現最好的 GPT-6 Astra（Codex 框架）Standard 成功率 34%；同一批 391 題上 Privileged 為 77%、Standard 為 30%。Realtime 在 54 題比較中，63% 的測試無代理解出，Standard 為 50%。同一模型換框架最多差 12 個百分點（Codex 34%、Claude Code 22%）。作者自己說明：每測試只跑一次、部分標籤由代理產生、結果僅限模擬。

白話：白話：讓會寫程式的 AI 去操控機器人解題。結果是，如果允許它看到模擬器內部、失敗就重來，它很強；一旦像真實機器人那樣只靠感測器、不能重來，成績掉一大截。
💡 為什麼重要你有 CV／機器人感知背景：這個結果直接說明『感知＋不可重置』才是難點。論文也顯示重置對成功率的幫助比完整狀態還大（28% 到 53%，對比 45%），也就是『能嘗試再修正』比『看得到全部』更重要。
🎯 對你的影響　👀 值得追蹤
與你的機器人感知背景相關（推測）：想知道編碼代理能不能代替手寫控制，這是目前少見的系統性評測；但全是模擬，距離真機還有落差。
▶ 想了解可去 Hugging Face Papers 讀 2611.12177 的 Standard 與 Privileged 對比章節，判斷你自己的專案環境更像哪一種設定。

評測設計

三種設定拉出『上限』與『真實條件』的差距；核心集 456 個困難任務（901 個測試）。

主要數字

Privileged 77% 對 Standard 30%；加入完整狀態使成功率由 28% 升到 45%，加入可重置升到 53%，兩者都加為 68%。

失敗型態

失敗常集中在任務的第一階段，需要精確對位的階段在 Standard 下失敗率明顯上升；較弱的代理常在接觸物體前就失敗。

框架影響

同一模型在不同 agent 框架差最多 12 個百分點，代表『模型分數』其實混了框架的作用。

訓練行為

足球任務中，只有環境有 GPU 與訓練函式庫時代理才會訓練策略，且勝出的都是訓練出的策略。

每個測試只跑一次；標籤部分由代理產生；全為模擬，不能直接推到真機。

🛡️ 研究

LEASH：給機器人 agent 加三道安全閘門，模擬中危害率由 11.23% 降到 0%

Hugging Face Papers 頁面（已讀全文摘要與結果）・11/10

論文提出 RoboRisk 基準與 LEASH 安全層。RoboRisk 涵蓋五類風險（任務拒絕、計畫修正、執行期危害、指令注入、序列記憶），92 個模擬任務與 13 個實體機器人任務；評估六個基礎模型與兩個機器人專用 API，基線危害率介於 9.06% 到 76.92%。LEASH 與模型無關、不需重訓規劃器，有任務、動作、提交三道閘門，用決策模型依當下相機畫面判斷，閘門預設用 Jev，也可用 OpenAI Decisions API。結果：模擬中 GPT-6 Astra 危害率 11.23% 降到 0.00%，成功率 78.99% 升到 80.80%；實體機器人上四個模型加入後成功率各為 84.62%，13 次執行未觀察到危害。閘門成本約每次執行 0.00522 美元，約占總成本 0.66%。以上為論文自己的數字。

白話：白話：機器人用大模型規劃動作時，只看幾何與力量限制不知道『把電子產品放進水裡』是壞事。LEASH 在執行前、每個動作、以及不可逆動作（如鬆開夾爪、倒液體）前各問一次小模型『這樣安全嗎』。
💡 為什麼重要這跟今天的 Decisions API 直接呼應：便宜快速的『判斷模型』被拿來當 agent 的閘門。你做個人助理或任何會動手的 agent，都可以借用『任務前、動作前、不可逆操作前』三段式檢查。
🎯 對你的影響　👀 值得追蹤
（推測）設計個人助理時，三段式閘門（任務前、動作前、不可逆前）可直接借用；與 Tap Diary 無關。
▶ 在你的助理工具清單中標出『不可逆』操作（刪檔、寄信、付款），先只對這類加一道人工或模型確認。

RoboRisk

五類風險；模擬 92 題、真機 13 題，閉環執行。基線危害率 9.06% 到 76.92% 差很大。

兩個專用 API 的問題

其中一個危害率 59.0%；另一個沒造成危害但成功率只有 28.2%，過度保守。

三道閘門

任務閘門在執行前審指令，是唯一能直接終止任務的；動作閘門審每個候選動作；提交閘門審不可逆操作。三者與規劃器共用同一份安全政策。

效率

主文：平均執行時間增加約 1.66%（針對兩個模型），閘門成本約 0.66%。

限制

效果取決於閘門準確度與規劃器是否遵守政策；目前決策模型推理有限，所以動作與提交閘門只能拒絕；提交閘門只涵蓋張夾爪與倒液；有模型仍因不遵循指令而有風險（實體 38.46%）。

📘 今日一課 · 10 分鐘

用『決策閘門』替 agent 把關：分類而不是生成

為什麼今天學這個

今天兩則新聞都用到同一個想法：Gemini Decisions API 提供便宜的『選項打分』端點，LEASH 論文把它放在機器人動作前當安全閘門。第 4 週課程已結案，這一課是依今天新聞延伸的新主題。內容依官方文章與論文摘要整理；下面的實作我沒有在此環境實際執行，也沒有呼叫 API。

是什麼

『決策閘門』是在 agent 做事之前先問一個封閉問題：這個請求要不要做？該走哪條路？危險嗎？答案只能是預先定好的選項（是／否、A／B／C、0 到 4 分），而不是一段自由文字。

為什麼不用一般 LLM 回答

生成式回答要逐字產生，慢、貴，格式還可能亂掉。封閉式判斷只需要一個選項與一個機率。依 Google 官方說法，Decisions API 就是為此設計：單次前向傳遞替選項打分，並附 0 到 1 的信心分數。

怎麼運作（概念）

輸入一份內容與一組問題；每題回傳各選項機率。程式拿機率做決定：機率高就自動放行或拒絕，信心低就交給更強的模型或人。重點是『信心門檻』，而不是模型本身。

LEASH 的三道閘門

論文把閘門放在三處：任務前（可直接終止）、每個動作前、不可逆操作前（如鬆開夾爪、倒液）。你的 agent 也可以對應：收到請求時、呼叫每個工具前、刪檔寄信付款之類不可逆動作前。

要小心的地方

閘門本身也會錯：論文就指出效果取決於閘門準確度，而且過度保守會讓成功率掉（它列出的某個專用 API 成功率只有 28.2%）。所以要用真實樣本量測誤擋與漏擋。

10 分鐘小實作

不用 API，先用假分數練『門檻邏輯』：把你的 agent 工具分成可逆與不可逆，替每一類決定『自動放行』『問人』『拒絕』的信心門檻，並寫成一個純函式，再用十組自編的分數測。

動手做（勾選記錄進度）

貼給 Claude Code 的指令

請用繁體中文幫我替我的專案設計一個『決策閘門』。先不要改任何檔案：1) 掃描專案中 agent 可呼叫的工具或函式，列表並標註可逆或不可逆；2) 為每個不可逆工具提出一個封閉式判斷問題（是／否或多選）；3) 寫出一個純函式 decide(prob, confidence) 的設計草稿，包含放行、問人、拒絕三種結果與建議門檻，並說明為什麼這樣設；4) 列出我該用哪些真實樣本量測誤擋與漏擋。若你不確定某個工具是否可逆，請直接說不確定，不要猜。
