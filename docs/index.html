Gemini 4 Carbon 發布：主打資安與長時程任務，目前僅限部分網路防禦者

Google・10/28

官方文章（10 月 28 日）稱 Gemini 4 Carbon 是目前最強模型，強項是資安與長時程任務。官方列出的數字：Artificial Analysis Intelligence Index v5.0 得 59 分、排名第一；SEC-bench Pro（找漏洞）88.2%、ExploitGym（驗證可利用性）54.8%、CWE-bench（修補根因）71.0%（皆不含護欄）；WebDev Arena 1768 分、排第 4。可用性：目前只開放給部分網路防禦者，之後經 Fairwind Program 擴大，開發者與一般用戶時程只寫「soon」。導入期價格每百萬 token 輸入 2 美元、輸出 10 美元，導入期後 4／20 美元。

白話：白話：Google 推出新旗艦模型，但先只給做資安防禦的人用。原因大概是它很會找與利用漏洞，所以先控制誰能用（此為推測，文章未直接這樣說明）。
💡 為什麼重要價格與使用範圍決定你能不能拿它來做日常開發。目前一般開發者還用不到，所以先看，不用動作。
🎯 對你的影響　👀 值得追蹤
目前不對一般開發者開放，你現在用不到；但資安與長時程能力若開放，可能影響你用 agent 寫與審查程式碼的選擇（推測）。
▶ 等開放 API 後，用你自己的小型 repo 比較它與目前慣用模型的修補品質，並先看快取折扣能否降低成本。

三項資安基準分別對應找漏洞、驗證能不能被利用、修補根因，官方註明為不含護欄的測試。ExploitGym 54.8% 代表約一半可利用性驗證成功，仍遠非全部；這些是官方說法。

官方轉述 Chrome 團隊回報，生成高品質修補的表現比另一實驗室的前沿模型好 10 倍以上；比較對象與方法文章沒有詳述，需保留看法。

Mistral Large 4 開放權重：約 1T 參數的 MoE、1M 上下文

Hugging Face 部落格・10/29

Hugging Face 部落格（10 月 29 日）介紹 Mistral Large 4：多模態（輸入文字與圖像、輸出文字）、多語言的 Mixture-of-Experts 模型，約 1T 總參數、約 49B 活躍參數（模型名稱寫 A52B，頁面未解釋差異），上下文 1M tokens。授權是 Mistral Ecosystem Open-Weight License，頁面稱為 MIT 衍生，對模型即服務有限制。官方版本有 FP8 與 NVFP4，另有 GGUF 量化版。頁面稱截至 10 月 29 日是 Artificial Analysis Intelligence Index 上第五名的開放權重模型。

白話：白話：MoE 是「模型很大，但每個 token 只啟動一小部分專家」，所以算得比總參數量便宜。權重公開，可以自己下載跑，但這麼大的模型不是一般電腦跑得動。
💡 為什麼重要你的第 3 週課程會談開放權重與閉源的取捨，這是很好的實例；第 4 週會談 GGUF 與量化，這篇也提到了。
🎯 對你的影響　👀 值得追蹤
1T 參數對你的本機環境不實用（推測）；但可作為之後比較開放權重與閉源模型的例子。
▶ 到 Hugging Face 的 Mistral Large 4 collection 看 FP8 與 GGUF 的檔案大小，估算自己需要多少記憶體。
📖 展開完整解析（5 段）

架構

文字解碼器 72 層，第一層為 dense，其餘 71 層為 MoE；每 token 由 router 從 128 個專家選 4 個，加 1 個共享專家。注意力結合 MLA 與 DeepSeek Sparse Attention 索引器，每個 query 最多選 2,048 個 key 位置。視覺端是約 1.6B 的 Pixtral 編碼器。

基準（頁面所報）

DeepSWE v1.1 61.7%、Terminal-Bench 4 28.3%、AutomationBench 59.9%、Cybench 40 題中解 93%。這些都是頁面轉述，我沒有逐一核對原始榜單。

怎麼取得

權重在 Hugging Face；Transformers、vLLM、llama.cpp 皆支援。頁面註明 NVFP4 版本在 vLLM 需要 NVIDIA Blackwell GPU；託管方式有 Inference Endpoints（8×H200 配方）與 Inference Providers。

使用注意

`reasoning_effort` 可設 low、medium、high（預設），頁面說推理無法關閉。授權對 model-as-a-service 有限制，商用前要讀授權全文（我沒讀）。

📘 今日一課 · 12 分鐘

多代理人：路由器加工作者，什麼時候值得拆？

為什麼今天學這個

課程第 2 週「Agent 與工具使用」最後一個主題是多代理人。今天電子報提到一個 agent 原型：一個長駐的路由器會話加上平行、隔離的工作者，並自報完成時間縮短（官方說法，我沒讀原文）。以下為一般原理，非來自原文；我沒有實際執行。

是什麼

多代理人是把一件大任務交給多個各自有獨立上下文的 agent：常見形狀是一個「協調者（路由器）」負責拆工作與收結果，多個「工作者」各做一塊。每個工作者只看自己需要的資料。

為什麼要拆

第 1 週學過上下文視窗有限且越長越貴。拆給工作者，每人的上下文都短；互相獨立的子任務還能平行跑，縮短時間。今天那個原型自報 p95 完成時間從 29.5 分鐘降到 15.7 分鐘，就是這類好處的例子，但未經獨立驗證。

怎麼運作

1) 協調者讀需求並拆成子任務；2) 每個子任務交給一個工作者，附上最少必要的資訊；3) 工作者各自使用工具完成並回傳摘要；4) 協調者整合結果。關鍵：工作者之間不共享上下文，所以交接的內容要寫完整。

代價與風險

成本通常更高（多次呼叫、重複讀資料）；交接資訊遺失會讓結果不一致；工作者若各自改同一個檔案會衝突。原型作者也承認沒有跨會話的長期記憶，是一個限制。

什麼時候不拆

任務小、步驟相依很強、或需要整體一致性時，單一 agent 通常更簡單可靠。先用單一 agent，遇到上下文塞不下或明顯可平行時才拆。
